SF4Enhanced · what's behind it

Inside SF4Enhanced

How a 2014 fighting game with dead online servers gained rollback netcode without a single game file being changed: the engine, the injection, the save states, GGPO, the lobby, the server, and what it takes to keep all of it running.

How you play

  1. Have Steam running. Extract the release anywhere except the game folder and run SF4Enhanced.exe. It finds the game by itself.
  2. Main menu, Multiplayer Battle. The lobby takes over the screen. Press Start on the controller you'll play with.
  3. One player chooses Create lobby and gets a code like K7PQ2M. The other chooses Join with code.
  4. Pick a character, costume, colour, Ultra and edition, then press Start to ready up. When both are ready, the fight begins.
  5. When it ends: Rematch, Change character or Leave.

The lobby is driven from the controller: d-pad or stick to move, A to confirm, B to go back, left and right along the options row, bumpers to change a value. Keyboard works too. Input delay lives on the home screen; two frames is a good start on a normal connection.

The game, and why this is possible at all

Ultra Street Fighter IV runs on an engine by Dimps. Four properties of the Steam build make a rollback mod feasible where it would be hopeless for most games.

  • One fixed binary. The executable has not changed in years and is loaded at the same memory address every run, because it was built without address randomization. Every function the mod needs sits at a known, stable offset.
  • Full class names inside the binary. The build kept its C++ runtime type information, all 975 class names, so any object in memory can be asked what it is. That turned days of guesswork into readable diagnostics.
  • A built-in save-state system. Training mode's "save position, load position" is implemented with memento objects: every battle subsystem knows how to write its state into a buffer and read it back. Rollback needs exactly that, dozens of times per second.
  • A deterministic, fixed-step simulation. The fight advances in exact 60ths of a second from a seeded random number generator. Given the same inputs, two machines compute the same fight, which is the entire premise of rollback.

How the mod gets in without touching a file

The mod is two programs. SF4Enhanced.exe is what you double-click. Sidecar.dll is the mod itself, and it only ever exists inside the running game.

The redirection is done with Microsoft Detours, a library Microsoft publishes for exactly this. The mod knows where each game function lives because a separate layer of the code, called Dimps after the engine, is a hand-built map of the executable: about two hundred functions and data fields, each at a fixed offset, produced by reverse engineering over several years by the original author.

Steam's own online modes are switched off while the mod runs, because the game is running outside Steam's normal launch path. That is why "Multiplayer Battle" opens the mod's lobby instead.

What rollback is, in plain terms

Online, your opponent's button press takes tens of milliseconds to reach you. The old approach, delay-based netcode, waits for it before showing anything, so every input feels late. Rollback does the opposite: it guesses that the opponent kept doing what they were doing, shows the frame immediately, and when the real input arrives a few frames later, it quietly rewinds the fight to that moment, replays the frames with the correct input, and continues. Done right, the guess is correct most of the time and the corrections are a few frames long and barely visible.

To do that, four things must be true, and each one maps to a piece of the mod:

  • The game must be able to save its entire fight state every frame and restore any recent one instantly. That is the memento system, extended.
  • The game must accept inputs from the network instead of the controller. That is the controller-read detour.
  • Given the same inputs, both machines must compute exactly the same fight. That is determinism, and it is what the verification tools exist to prove.
  • Something must run the prediction, rewind and replay bookkeeping and the networking. That is GGPO.

How GGPO was added

GGPO is the open-source library that pioneered rollback for fighting games. It does not know anything about Street Fighter. It asks the game for five things through callbacks: save your state, load a state, advance one frame, tell me your inputs, and here are the synchronized inputs for this frame. The mod supplies all five from inside the detoured battle loop.

The save state, and what the game did not save

The clever part of the original design is that the game's memento buffers are not copied. Each frame, the mod asks every subsystem to record itself, then steals the buffers and hands the game empty ones. Loading a state is putting the stolen buffers back and asking every subsystem to restore. That is fast enough to do sixty times a second.

Training mode only needed to save what a paused fight needs, so several things were never in the mementos and had to be added by hand: the battle's state machine, the HUD announcements, the Scaleform animation pool that drives everything drawn over the fight, the engine's task scheduler, and a full model of which sounds are playing. Each of those is a place where a subtle mistake shows up as a desync, which is why the next section exists.

Two other things that had to be true

  • Same random numbers. The lobby's creator picks a seed and both games start the match from it.
  • No pausing. Pause is disabled during an online match, since one side pausing would mean the other side predicting forever.

Proving it works, and what was found

Rollback fails silently: nothing crashes, the two players just slowly end up in different fights. So the first work on this fork was tooling that makes that failure visible and attributable, without needing a second player.

Results so far

  • fixed Scaleform animations restored in the wrong order. The HUD animation pool was restored first and then disturbed by a later subsystem's restore. Restoring it last removes the difference entirely; confirmed across four independent runs.
  • fixed Matches dropped after a one-second network hiccup; the timeout is now ten seconds. Time-sync froze the whole game for up to 130 ms; it now skips frames while rendering continues.
  • fixed A crash on device reset (alt-tab out of fullscreen), a copy-paste slip that broke the training HUD after every restore, and log output that silently lost the end of every run.
  • open Both character actors lose some state on restore. Deterministic, localized to runs of 3D vectors near the end of each actor's memento, and not converging after repeated restores. The gameplay-divergence counter will say whether it changes matches in practice; across the first dozens of real online matches it has not produced a visible desync.

The lobby server: codes, a relay, and no port forwarding

Two games behind two home routers cannot talk to each other directly. The original project required both players to forward ports and exchange IP addresses. SF4Enhanced replaces that with a small server that both games connect out to, and an in-game lobby in front of it.

What the server enforces

  • Twenty lobbies, two players each. Empty lobbies are recycled after ninety seconds.
  • The lobby remembers the creator's build hash; a joiner with a different build is refused with a clear message, so mismatched versions never desync each other.
  • Relay endpoints time out after twenty seconds of silence.

The address of the server is built into the launcher and never shown on screen; the lobby's home screen only reports whether it is online. Anyone can run their own server from the release's server package, and a server.txt next to the launcher quietly overrides the built-in one.

How it is managed

Code

  • Fork at github.com/fabeloper/sf4e. The original Codeberg repository is the upstream remote so its engine fixes can be merged.
  • The engine map in src/Dimps is kept unmodified; fork work lives in src/sf4e, src/session and src/server.
  • Every change is a commit with a message explaining what was measured, not just what was typed.

Build

  • Visual Studio 2022 Build Tools, 32-bit, plus vcpkg for dependencies.
  • deploy/pack-all.cmd builds both packages and bakes the server address from a local file that never enters the repository.
  • The game must not be running during a build; Windows locks the loaded DLL.

Release

  • Two artifacts per release: the player zip and the server zip, tagged and published on GitHub.
  • Version gating is automatic through the build hash: old and new builds refuse each other.

Server

  • Runs on any Windows machine. Today: a spare laptop, lid closed, wired to the home router, with a one-time setup script that opens the firewall, prevents sleep and restarts it at boot.
  • lobby.log shows every create, join and relay pairing.

Bug reports

  • %APPDATA%\sf4e\logs\sf4e.log from both players, with network stats logged every ten seconds.
  • The newest file in %APPDATA%\sf4e\crash\ if the game closed.
  • Characters, who created the lobby, and what each player used to play.

Ports (all UDP)

  • 23400 matchmaker
  • 23401-23420 one session per lobby
  • 24001-24020 one relay per lobby

Next steps, in order

1

More players, more logs

Every match logs ping and frames-behind on both sides and counts gameplay divergences. The next questions, whether the relay is fast enough across countries and whether the actor gap ever changes a match, are answered by volume.

2

A permanent address, then a rented server

A dynamic-DNS name so the built-in address never goes stale, then a VPS so nobody's laptop has to be on. After that, try a direct peer connection first and keep the relay as the fallback.

3

Portraits and polish

Character portraits and stage previews in the lobby, a ping readout before you ready up, and a spectator seat.

4

Close the actor save-state gap

Read the character actor's save and restore routines in the disassembly to find which fields one writes and the other does not. The diagnostics are in place to confirm the fix in minutes.
